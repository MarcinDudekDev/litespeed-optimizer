LiteSpeed vs FrankenPHP — matched worker mode

Projectlitespeed-optimizer × ultrafastwoo Date2026-06-16 Origin-local Verdict: engine/SAPI, not process model

Summary

Pass-2 left one caveat open: the LiteSpeed win might be only a process-model artifact, since the as-deployed FrankenPHP ran classic mode (full WordPress bootstrap per request) while LiteSpeed ran persistent children. Pass-3 closes it. ultrafastwoo built and deployed real FrankenPHP worker mode on the big box (reversible, Marcin-authorized, 16 workers to match LiteSpeed, with a per-request WP+WooCommerce state reset that passed live cart-isolation tests).

The gap did not close — it stayed. With FrankenPHP now skipping bootstrap entirely (worker mode) and LiteSpeed's lsphp still doing a full bootstrap on every request, LiteSpeed is still ~25% faster on uncached render and ~6.6× faster on the cart path. That inverts the structural advantage and points the finger at the engine / SAPI itself: LSAPI's per-request execution is simply faster than FrankenPHP's for this WooCommerce workload. And FrankenPHP worker mode turned out to be a net-zero perf change versus its own classic mode — correct and leak-safe, but not a win for a cart-bearing Woo app, because the state-reset it needs costs about as much as the bootstrap it skips. Pass-3 supersedes Pass-2's conclusion.

FrankenPHP classic (4 threads)Thread-per-request, fresh interpreter stateYes — full WP bootstrap every request

Key point: lsphp is not “worker mode” in the FrankenPHP sense. It re-bootstraps WordPress per request — the thing worker mode exists to avoid — and still wins. So the comparison is no longer worker-vs-bootstrap; it is engine-vs-engine.

Verdict

FrankenPHP worker mode skips the WordPress bootstrap; LiteSpeed's lsphp does not. LiteSpeed still wins ~25% on render and ~6.6× on cart. The difference is the engine/SAPI, not the process model — and FrankenPHP worker mode is a net-zero change over its own classic mode for this Woo app. — Pass-3, superseding Pass-2

Why worker mode nets zero here

The cart-safety reset costs about as much as the bootstrap it skips. WordPress is not worker-safe by default, and WooCommerce least of all — WC()->cart, session, and customer would leak across customers in a resident worker. To stay correct, the worker re-runs, every request: a fresh WC_Cart, WC_Customer (read), session re-initialization, and a runtime cache flush. That mandatory reset is roughly as expensive as the classic bootstrap it replaces — which is exactly why FrankenPHP-worker ≈ FrankenPHP-classic on both boxes (big: ~7% faster; ultrafastwoo's local MariaDB before/after: worker 29.8/31.5/30.6 vs classic 26.7/28.0/28.5 ms — a hair slower). Worker mode is still the right call for correctness — it passed live cart-isolation smoke tests — it just is not a performance win for a cart-bearing WooCommerce store.
