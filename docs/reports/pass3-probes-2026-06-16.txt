KEY CORRECTION (ultrafastwoo): lsphp is NOT app-worker mode. It is a persistent PROCESS pool
(php-fpm-style): the 16 children stay alive but each request does a FULL WP bootstrap (opcache hot).
FrankenPHP-worker, by contrast, keeps WP RESIDENT and SKIPS bootstrap entirely.
=> So FrankenPHP-worker has the structural advantage (no bootstrap) and lsphp does the "expensive" thing
   (full bootstrap every request) — yet lsphp STILL beats FP-worker ~25% on render and ~6.6x on cart.

VERDICT (Pass-3 SUPERSEDES Pass-2): the gap is the ENGINE / SAPI, not the process model.
  - Pass-2 framed the gap as "FrankenPHP-classic vs LiteSpeed-worker process-model mismatch." Pass-3
    matches FrankenPHP to worker mode (its best case, bootstrap skipped) and the gap does NOT close —
    lsphp's per-request execution (LSAPI) is simply faster than FrankenPHP's for this Woo workload.
  - Worker mode nets ZERO for this Woo app (corroborated on BOTH boxes):
      * big origin: FP-worker ~7% faster than FP-classic render (noise).
      * ultrafastwoo LOCAL before/after (MariaDB, median-15): WORKER 29.8/31.5/30.6 vs CLASSIC 26.7/28/28.5
        — worker a HAIR SLOWER. The per-request cart-safety reset (new WC_Cart + WC_Customer(read) +
        initialize_session + runtime cache flush, every request) costs ~as much as the bootstrap it skips.
  - Worker mode IS leak-safe + correct (live cart-isolation smoke clean) — it just isn't a perf win for a
    cart-bearing WooCommerce app.
