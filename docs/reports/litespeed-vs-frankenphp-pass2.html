LiteSpeed vs Caddy / FrankenPHP — same Datastar app

Projectlitespeed-optimizer × ultrafastwoo Date2026-06-16 Origin-local Verdict: process-model mismatch

Summary

Pass-2 makes the web server the only variable: ultrafastwoo's exact SQLite install (WordPress 7.0 / WooCommerce 10.7 / Datastar theme / 500 products) was cloned onto the LiteSpeed box as an isolated vhost (ufwbench.loc:8443, lsphp84, 16 persistent worker children, LSCache), serving the same pages as the as-deployed Caddy/FrankenPHP demo on the big box.

Serving identical cached pages, the two stacks tie at the edge (LSCache vs Souin, both single-digit ms). On uncached render the LiteSpeed clone is ~25–40% faster and far steadier under load — but the honest reason is a process-model mismatch, not an engine win: the as-deployed FrankenPHP runs in classic mode (full WordPress bootstrap on every request, num_threads:4), while the LiteSpeed clone runs persistent worker children that skip bootstrap. FrankenPHP's worker-mode and watch settings were present but dead config (the Caddyfile's bare frankenphp directive has no config placeholder, so both are silently ignored). FrankenPHP can run worker mode, but plain WordPress is not worker-safe — it needs a worker.php wrapper + patches, a separate dev task and Marcin's call. So there are no “tuned matched-worker” numbers to wait for; this is the verdict.

LiteSpeed-worker vs FrankenPHP-classic As-deployed: LiteSpeed faster on render & load

As deployed, the LiteSpeed clone (16 persistent lsphp worker children) serves uncached pages ~25–40% faster and holds up far better under cart-heavy load than the FrankenPHP demo — because FrankenPHP is running classic mode (full WordPress bootstrap per request), not its persistent worker mode. Its worker-mode + watch directives are present but inert: the Caddyfile's bare frankenphp block has no config placeholder, so they are silently ignored (admin API apps.frankenphp = {}, no worker metrics). Forcing worker mode refused to boot — plain WordPress index.php never reaches frankenphp_handle_request(); real worker mode needs a worker.php wrapper plus WP worker-safety patches. That is a separate dev task and Marcin's call, not a benchmark knob — so this verdict is final, with the explicit caveat that it compares two different process models, not two PHP engines head-to-head.

Carry-over foot-gun from Pass-1

OLS perClientConnLimit + Cloudflare real-client-IP. OpenLiteSpeed self-protects against single-IP floods (default ~20 conn / 40 static-rps / 2 dyn-rps per IP). Cloudflare forwards the real client IP, so a single-client k6 run through CF trips that limit and produces an HTTP 520 storm — which reads as a LiteSpeed “loss” but is a security feature, not a capacity ceiling. Always benchmark OLS origin-local. The mirror-image gap on the Caddy side: no origin per-IP cap, so it leans entirely on CF + origin firewalling. A security trade-off on each side, not a speed gap.
